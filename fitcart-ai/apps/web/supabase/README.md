# FitCart AI — Supabase backend setup

One-time steps to go from placeholder env vars to a live backend.

1. **Create a Supabase project** at supabase.com (free tier is enough to start).

2. **Run the schema.** Dashboard → SQL Editor → New query → paste the full contents of `schema.sql` → Run.

3. **Enable Google OAuth.** Dashboard → Authentication → Providers → Google → toggle on, then supply a Google Cloud OAuth 2.0 Client ID + Secret (create one at console.cloud.google.com → APIs & Services → Credentials → OAuth client ID → Web application; add the Supabase callback URL shown in the provider panel as an authorized redirect URI).

4. **Install the Supabase CLI** (`npm i -g supabase`) and link this project: `supabase login`, then `supabase link --project-ref <your-project-ref>` from `fitcart-ai/apps/web`.

5. **Set Edge Function secrets:**
   ```
   supabase secrets set STRIPE_SECRET_KEY=sk_test_...
   supabase secrets set STRIPE_WEBHOOK_SECRET=whsec_...
   supabase secrets set SUPABASE_SERVICE_ROLE_KEY=<from Dashboard -> Project Settings -> API>
   ```
   (`SUPABASE_URL` is injected automatically into Edge Functions — no need to set it.)

6. **Deploy the Edge Functions:**
   ```
   supabase functions deploy create-checkout-session
   supabase functions deploy stripe-webhook --no-verify-jwt
   supabase functions deploy fetch-product
   supabase functions deploy search-products
   supabase functions deploy populate-catalog
   supabase functions deploy curate-match
   supabase functions deploy curate-product
   ```
   (`populate-catalog`, `curate-match`, and `curate-product` are all optional — see 7e/7f/7g below — but deploying any of them costs nothing if you don't call it.)

7. **Point a Stripe webhook at `stripe-webhook`.** Stripe Dashboard (test mode) → Developers → Webhooks → Add endpoint → URL is `https://<project-ref>.supabase.co/functions/v1/stripe-webhook` → events: `checkout.session.completed`, `customer.subscription.updated`. Copy the signing secret into step 5's `STRIPE_WEBHOOK_SECRET`.

7b. **(Optional) Enable live Amazon/Flipkart search on Discover.** `search-products` powers the "search live listings" box — without credentials (and without `MOCK_MARKETPLACES`, see below) it correctly returns `not_configured` per-provider rather than any placeholder data (that's deliberate, not a bug to work around). To turn it on:

   > **Why this section looks nothing like older Amazon integration writeups.** Amazon's Product Advertising API v5 (PA-API v5) was deprecated April 30, 2026 and fully retired May 15, 2026 — every PA-API v5 call now returns a hard `403 AccessDeniedException`, regardless of how correct the old AWS-SigV4-signed integration is. This migration to the **Amazon Creators API** (OAuth2, not AWS request signing) was necessitated by that retirement, not a stylistic preference. If you find PA-API v5 setup instructions elsewhere (older blog posts, AI-generated code, etc.), they will not work against a live account anymore. Sources:
   > - https://affiliate-program.amazon.com/creatorsapi/docs/en-us/paapiv5-deprecation
   > - https://affiliate-program.amazon.com/creatorsapi/docs/en-us/migrating-to-creatorsapi-from-paapi
   > - https://dev.to/th3nate/amazon-pa-api-v5-is-shutting-down-april-30-2026-here-is-what-changes-at-the-auth-layer-22ek

   - **Amazon Creators API**: apply for an Amazon Associates account, then create a Creators API app at Associates Central -> Tools -> CreatorsAPI -> Create App to get a Client ID (`amzn1.application-oa2-client...`) and Client Secret — these are OAuth2 credentials, not AWS Access/Secret Keys, and old PA-API keys do not carry over. **Eligibility bar is materially harder than PA-API v5's old rule and must be actively maintained, not just reached once**: Creators API requires **10+ qualified sales in the trailing 30 days** (PA-API v5 required only 3+ sales in the trailing 180 days) — this is a rolling window, so access is temporarily revoked if any 30-day period passes with fewer than 10 qualifying sales, even for a previously-approved account. Once approved, set:
     ```
     supabase secrets set AMAZON_CREATORS_CLIENT_ID=...
     supabase secrets set AMAZON_CREATORS_CLIENT_SECRET=...
     supabase secrets set AMAZON_CREATORS_PARTNER_TAG=...
     ```
     Optional overrides:
     ```
     supabase secrets set AMAZON_CREATORS_TOKEN_URL=https://api.amazon.com/auth/o2/token
     supabase secrets set AMAZON_CREATORS_MARKETPLACE=www.amazon.in
     ```
     `AMAZON_CREATORS_TOKEN_URL` defaults to the standard Login-with-Amazon token endpoint. **Unverified**: we could not confirm during this integration pass whether the India marketplace requires a region-specific token host — confirm against your actual Associates Central region docs before relying on the default in production, and override via this secret if it differs.
   - **Flipkart Affiliate API**: apply at affiliate.flipkart.com — unchanged, still current (confirmed against the [official docs](https://affiliate.flipkart.com/api-docs/af_prod_ref.html)). Once approved, set:
     ```
     supabase secrets set FLIPKART_AFFILIATE_ID=...
     supabase secrets set FLIPKART_AFFILIATE_TOKEN=...
     ```
   - Myntra, AJIO, Meesho, and Nykaa Fashion have no public catalog/search API — unlike Amazon/Flipkart, `configured()` is hardcoded to always return `false` for these four (see `orchestrator.ts`'s `PROVIDERS` table), so they permanently run through the same best-effort live-scrape fallback described in 7d below, not a real credentialed API. They're also still reachable via `fetch-product`'s paste-a-link flow (Home page) for a single known URL.

7c. **(Optional, dev/demo only) Mock marketplace mode.** If you want Discover's search box to return something without either affiliate account approved yet, set:
   ```
   supabase secrets set MOCK_MARKETPLACES=true
   ```
   With this on, `search-products` skips real Amazon/Flipkart calls entirely and returns fake listings (obviously-fake `example.com` URLs, tagged `source: 'mock'` in the response and persisted as `amazon-mock`/`flipkart-mock` in the `products.source` column — see `schema.sql`). **Never set this on a production Supabase project** — there is no structural separation between mock and real catalog rows beyond that string tag, so a real+mock collision would let demo rows silently blend into the real catalog. Every invocation while this is active logs a loud warning server-side.

7d. **Request/response contract (6 stores).** `search-products` takes `{ query: string, marketplace?: 'amazon' | 'flipkart' | 'meesho' | 'myntra' | 'ajio' | 'nykaaFashion' | 'all' }` (`marketplace` defaults to `'all'`) and always responds `200` for a well-formed request — per-provider outcomes (including `not_configured` or an upstream failure) live inside the `providers` object, not the HTTP status, so one provider's trouble never masks the other's results:
   ```jsonc
   {
     "query": "men's shirt",
     "mock": false,
     "results": [ /* merged StoreListing[] across all queried providers */ ],
     "providers": {
       "amazon":       { "status": "success", "count": 4, "upserted": 4 },
       "flipkart":     { "status": "not_configured", "count": 0, "upserted": 0, "message": "Flipkart search isn't connected yet." },
       "meesho":       { "status": "scrape_blocked", "count": 0, "upserted": 0, "message": "Meesho isn't connected yet, and the scraping fallback was blocked: HTTP 403 from Meesho" },
       "myntra":       { "status": "success", "count": 3, "upserted": 0, "message": "Served 3 results from the local catalog (previously fetched) — no new live request was made to Myntra this time." },
       "ajio":         { "status": "scrape_blocked", "count": 0, "upserted": 0 },
       "nykaaFashion": { "status": "scrape_blocked", "count": 0, "upserted": 0 }
     }
   }
   ```
   `400` is returned only for malformed input (missing/empty `query`, `query` over 200 characters, or an unrecognized `marketplace` value). `500` is returned only for a genuine unhandled error, with a sanitized client-facing message — full detail (which may include upstream response bodies) goes to `console.error` server-side only, never to the client or logged verbatim with un-sanitized input.

   **Local-cache-first (new).** Before touching a real API or attempting a live scrape for a requested store, `search-products` checks the `products` table itself (`localCatalog.ts`'s `findCachedListings`, matching on `name`/`brand`/`category` via case-insensitive `ilike`, excluding any row whose `source` ends in `-mock`). If there are at least `MIN_CACHE_RESULTS` (currently **5**) real matches, those are returned directly and *no* real API call or live scrape is attempted for that store at all this request — `status` is still `"success"`, `upserted` is `0` (nothing new was fetched), and `message` says the results came from the local catalog. If there are *some* but fewer than 5 matches, those are kept and merged (deduped by `productUrl`) with whatever the real API/scrape attempt below returns, rather than being thrown away. See `populate-catalog` (7e below) for proactively warming this cache.

   **Real API / scraping fallback statuses.** For a store not served entirely from cache, `search-products` tries the real affiliate API when configured (Amazon/Flipkart only), otherwise attempts a best-effort live scrape of that store's own search-results page (`supabase/functions/search-products/scraping/`; see the "Known limitations" entry below for what was actually observed doing this) — this is the *only* path for Meesho/Myntra/AJIO/Nykaa Fashion, which have no real API to configure at all. That attempt's outcome adds two more possible `providers.<store>.status` values on top of the existing `success` / `not_configured` / `error` / `mock`:
   - `scrape_blocked` — the scrape ran but didn't produce usable results (a non-2xx response, a 200 response that couldn't be parsed as real listings — almost always a bot-check page, or a real page with no price data — or results that got dropped by the outbound-link allowlist). `message` states both facts honestly, e.g. `"Amazon isn't connected yet, and the scraping fallback was blocked: HTTP 403 from Amazon"`.
   - `scrape_failed` — the scrape attempt itself threw (network/DNS/timeout-level failure), not a parse problem. `message` follows the same "isn't connected yet, and the scraping fallback failed: ..." shape.

   A successful scrape reports `status: "success"` exactly like a real API response, but every listing it contributes to `results` carries `"source": "scraped"` (as opposed to `"source": "live"` for a real API response or a sufficiently-cached result, or `"source": "mock"` under `MOCK_MARKETPLACES`) — so the frontend/DB can always tell a scraped listing apart from an affiliate-API one, per D-014 (never present data as more/less trustworthy than it actually is). `MOCK_MARKETPLACES` is checked before any of this — mock mode always short-circuits before the cache lookup *and* before a real scrape is ever attempted (see the "Tests" section for this specifically).

7e. **(Optional) `populate-catalog` — proactively warm the cache.** A separate Edge Function, `supabase/functions/populate-catalog/`, that runs the exact same fetch/scrape/upsert logic as `search-products` across a batch of `(search term, store)` pairs ahead of any real user request, so those searches can later be served from the local cache above instead of a live attempt. It is:
   - **Secret-gated.** Every request must send a `x-populate-secret` header matching the `POPULATE_CATALOG_SECRET` secret (set it yourself — this is not a client-exposed value, and there is no default):
     ```
     supabase secrets set POPULATE_CATALOG_SECRET=<a long random value you generate>
     ```
     A missing/wrong header is a `401` with no detail about the correct value; the header is never logged.
   - **POST-only**, body `{ terms?: string[]; stores?: Store[] }` — both are optional. Omitting `terms` uses the first 5 entries of the curated list in `searchTerms.ts`; omitting `stores` uses all 6. Example:
     ```
     curl -X POST https://<project-ref>.supabase.co/functions/v1/populate-catalog \
       -H "x-populate-secret: <your secret>" \
       -H "Content-Type: application/json" \
       -d '{"terms": ["shirts", "jeans"], "stores": ["amazon", "flipkart", "meesho"]}'
     ```
   - **Capped per invocation** — `terms.length * stores.length` is capped at 24 pairs per call (a `400` if exceeded, not a silent truncation) to stay well inside an Edge Function's wall-clock budget given the scrapers' own 15s timeouts. **You are expected to call this multiple times** with different `terms`/`stores` slices to cover the full `searchTerms.ts` list across all 6 stores — there is no cron/scheduler wired up for this (see `DECISION_LOG.md` for why that's deliberate, not an oversight).
   - Response is a per-pair summary (`status`/`count`/`upserted`/`message`, identical shape to `search-products`'s per-provider report) plus `totals`.
   - There's a short (~350ms) delay between pairs — politeness/spreading out request volume, not a hard anti-detection guarantee (nothing here defeats real bot detection — see the live-test findings below).

7f. **(Optional) `curate-match` — manual cross-store price-comparison curation.** A separate Edge Function, `supabase/functions/curate-match/`, for a human curator to explicitly group product rows that are the same real-world item across different stores (e.g. the same jeans, in the same color, listed on both Amazon and Myntra), so the frontend can eventually show "cheaper elsewhere" comparisons. **This is manual curation only — it is explicitly NOT automated similarity matching.** An earlier design considered scoring product title/image similarity to auto-suggest matches; that approach was evaluated and rejected as unreliable for this catalog, since a false match (silently showing two different products as "the same item, cheaper elsewhere") is actively misleading to a shopper — worse than showing no comparison at all (D-014: never present data as more/less trustworthy than it actually is). `curate-match` never computes or suggests which product ids belong together — it only ever records the exact id list a human curator submits in the request body.
   - **Secret-gated**, with its own secret (not a reuse of `POPULATE_CATALOG_SECRET` — this is a distinct admin capability):
     ```
     supabase secrets set CURATE_MATCH_SECRET=<a long random value you generate>
     ```
     Every request must send a matching `x-curate-match-secret` header. A missing/wrong header is a `401` with no detail about the correct value; the header is never logged.
   - **POST-only**, body `{ productIds: number[], label: string, createdBy: string }`:
     - `productIds` — 2 to 10 distinct positive integers, each no greater than `Number.MAX_SAFE_INTEGER` (a JSON id above that could lose precision in transit and collide with an unrelated real `bigint` product id), and every one of which must already exist as a row in `products`. Checked against the real DB, never assumed — an id that doesn't exist is a `400`, not silently skipped.
     - `label` — a non-empty, human-readable description of the matched item (e.g. `"Levi's 511 Slim Jeans, Indigo"`), capped at 200 characters.
     - `createdBy` — a non-empty free-text curator identity (e.g. an email) recorded for accountability. No integration with an auth system for v1 — it's trusted as given once the shared secret has authorized the request.

     Example:
     ```
     curl -X POST https://<project-ref>.supabase.co/functions/v1/curate-match \
       -H "x-curate-match-secret: <your secret>" \
       -H "Content-Type: application/json" \
       -d '{"productIds": [101, 205], "label": "Levi'\''s 511 Slim Jeans, Indigo", "createdBy": "you@example.com"}'
     ```
   - **A product may only belong to one match group — enforced at the database level, not just in application code.** `product_match_members.product_id` carries its own `unique` constraint (`schema.sql`), so this is a real DB-enforced guarantee with no race window, not merely an app-layer check. `createMatchGroup` (`matchGroups.ts`) still does an app-layer SELECT first, purely as a fast path that gives a clean, specific `400` naming the conflicting product, group id, and group label (e.g. `"product 205 is already in match group 3 (\"Levi's 511 Slim Jeans, Indigo\")"`) in the common, non-racing case — but that SELECT-then-INSERT sequence alone would leave a TOCTOU race window (two concurrent requests with an overlapping `productId` could both pass the pre-check before either request's INSERT lands). The `unique` constraint closes that window entirely: if a concurrent request wins the race, the member `INSERT` itself fails with a Postgres unique-violation (`23505`), which `matchGroups.ts` catches and maps to the same clean `400` (with the just-created group row rolled back, same as any other member-insert failure) — never a generic `500`, and never a silent double-membership regardless of request timing/ordering.
   - **No partial/orphaned groups.** The group row and its member rows are created as one logical operation. There's no client-side multi-table transaction available here, so if the member insert fails after the group row was created, the group row is deleted again before responding — a failed request never leaves an empty group behind. If that cleanup itself fails (rare), the response says so explicitly (naming the orphaned group id, so it can be cleaned up by hand) rather than claiming a rollback that didn't actually happen.
   - Response on success: `200` with `{ id, label, createdBy, productIds }` for the newly created group. Every validation/integrity failure is a specific `400` — unknown product id, wrong `productIds` count/shape, duplicate ids, product already in another group, missing/empty/too-long `label` or `createdBy` — never a vague "something went wrong".
   - Schema: `product_match_groups` (one row per curated match) and `product_match_members` (one row per `(group, product)` pairing, `on delete cascade` from both parents, `product_id` additionally `unique` — see the "may only belong to one match group" bullet above) — see `schema.sql`. Both tables are public-read (RLS `select` policy, matching `products`' own read model) so the frontend can query them directly with the anon key once it's ready to render comparisons; only the service role (via this function) can write.
   - **`created_by` is not publicly readable — and getting this right required more than the obvious fix.** The two tables' `select` RLS policies are row-level (public read), but `product_match_groups.created_by` (a curator's identity/email) needs to stay hidden from the anon key even though the rest of that row is meant to be public. RLS can't do this alone (a policy controls which *rows* are visible, not which *columns* of a visible row are) — but the first fix attempted here, a bare `revoke select (created_by) on product_match_groups from anon, authenticated`, turned out to be a **silent no-op**: it produced no error and looked correct in `schema.sql`, but a live REST call for `?select=created_by` still returned the value. Verified directly against the live project (2026-09-03) via `has_column_privilege`/`pg_attribute.attacl`: Supabase grants every new table full table-level `SELECT` to `anon`/`authenticated` by default, and in Postgres a column-level privilege can only *add* access on top of a narrower table-level grant — it can never *narrow* a broader one. The actual fix (in `schema.sql` now) revokes `product_match_groups`' table-level `SELECT` entirely and re-grants it column-by-column for just `id, label, created_at` — confirmed live afterward: `?select=created_by` now correctly `401`s (`permission denied for table product_match_groups`), `?select=id,label,created_at` still works, and `?select=*` also `401`s (expected — `*` expands to every column, including the restricted one, so Postgres denies the whole request; not a bug, and confirmed nothing in `src/` queries this table with `*` — `fetchMatchGroup` only ever reads `product_match_members`/`products`, never `product_match_groups` directly).
   - There is currently no "list existing groups" endpoint — this is an internal curator tool, not a queryable admin API, so reading back what's been curated is a direct `select` against the two tables above (both public-read) rather than a third capability of this function.

7g. **(Optional) `curate-product` — manual product-detail curation (description, image gallery, size chart).** A separate Edge Function, `supabase/functions/curate-product/`, for a human curator to add richer per-product data — a real prose description, a size chart (`chest`/`waist`/`inseam`-style, shape varies by category), and an additional image gallery — beyond what the scraper/affiliate pipeline ever populates. **This is manual curation only, the same "not scraping, not fabrication" pattern `curate-match` already committed to for cross-store price matching, for the same reason: a real headless-browser scraping test (Playwright, run live against Myntra/AJIO/Meesho) confirmed the block on this data is network/IP-level (Akamai edge bot-management), not header-based — scraping it is not realistically achievable, so the project owner explicitly chose manual curation instead.** `curate-product` never extracts or infers this data from anywhere — it only ever writes the exact field values a human curator submits in the request body.
   - **Secret-gated**, with its own secret (not a reuse of `CURATE_MATCH_SECRET` or `POPULATE_CATALOG_SECRET` — same reasoning `curate-match` itself already gives for not reusing `populate-catalog`'s secret: this is a distinct admin capability, with a distinct blast radius, and rotating/revoking one secret must never affect the others):
     ```
     supabase secrets set CURATE_PRODUCT_SECRET=<a long random value you generate>
     ```
     Every request must send a matching `x-curate-product-secret` header. A missing/wrong header is a `401` with no detail about the correct value; the header is never logged.
   - **POST-only**, body `{ productId: number, description?: string, material?: string, sizeChart?: Record<string, unknown>, imageUrls?: string[] }`:
     - `productId` — required, a positive integer no greater than `Number.MAX_SAFE_INTEGER` (same float-precision id-collision guard `curate-match` uses for its own `productIds`), and must already exist as a row in `products` — checked against the real DB, never assumed.
     - Every other field is **optional, but at least one must be present** — a genuine partial-update endpoint, since a curator might add only a description today and a size chart later. A request with `productId` and nothing else is a `400` ("nothing to update"). Fields the curator doesn't mention are left completely untouched (never blanked out) — the underlying `UPDATE` only ever sets the columns actually present in the request.
     - `description` — a string, capped at 5000 characters (real prose, capped generously but not unbounded).
     - `material` — a string, capped at 200 characters (same cap `curate-match` uses for its own `label`). **`color` is deliberately NOT a curator-writable field here**, unlike `material` — `color` is part of the fixed column list `search-products/persistCatalog.ts`'s `upsertListings` writes on every re-scrape of a product's `product_url`, so a curator-set `color` value would be silently reverted the next time that product gets re-scraped. `material` has no such conflict (see the "safe from being silently overwritten" bullet below), which is what makes it safe to curate here.
     - `sizeChart` — must be a real JSON object if present (not an array, string, number, or `null`) — deliberately loose-shaped rather than a rigid schema, since different categories have different chart layouts (chest/waist for tops, waist/inseam for bottoms), but its serialized size is capped at ~4KB against a pathologically huge payload.
     - `imageUrls` — an array of strings, capped at 10 entries (a gallery, not unlimited) and 2000 characters per URL. **Every URL must additionally pass `search-products/urlAllowlist.ts`'s `isAllowedMarketplaceUrl` for the product's own `store` column** (looked up from the DB, never trusted from the request) — the exact same domain-allowlist defense the scraping pipeline already applies to `product_url`/`image_url` at ingest time, now applied to curator input too, since a compromised/malicious curator input is exactly the kind of thing that check already exists to catch elsewhere in this codebase. A request with even one disallowed URL is rejected whole, naming which URL failed and why — nothing is partially saved. A product whose `store` value isn't one of the six recognized marketplaces (see `urlAllowlist.ts`) can't have `imageUrls` validated at all and is rejected the same way; its other fields can still be updated normally. The `UPDATE` itself is also scoped by that same just-looked-up `store` value (not just `productId`), so if the row's `store` changes between the lookup and the write (e.g. a concurrent re-scrape) the write matches zero rows and is reported as a clean `400` conflict asking the caller to retry, rather than silently persisting `imageUrls` that were validated against a now-stale `store`.

     Example (adding a description and a size chart to an existing product):
     ```
     curl -X POST https://<project-ref>.supabase.co/functions/v1/curate-product \
       -H "x-curate-product-secret: <your secret>" \
       -H "Content-Type: application/json" \
       -d '{"productId": 101, "description": "A relaxed-fit cotton oxford shirt.", "sizeChart": {"chest": "38-40in", "length": "28in"}}'
     ```
   - `image_urls` is a **new gallery column, additive to the existing single `image_url`** (which stays exactly as-is — every existing read path already depends on it). See `schema.sql`'s comment on `products.description`/`products.image_urls` for the full column list.
   - **Why `material`, `size_chart`, `description`, and `image_urls` are all safe from being silently overwritten by a future re-scrape.** `search-products/persistCatalog.ts`'s `upsertListings` is the only code path that writes scraped/affiliate rows into `products`, and its upsert payload names an explicit, fixed column list: `name, brand, store, category, price, mrp, color, product_url, image_url, source, scraped_at`. PostgREST's upsert-on-conflict (`onConflict: 'product_url'`) only ever updates columns actually present in the payload — any column not named there is left completely untouched by a re-scrape of the same `product_url`. `material` has relied on exactly this guarantee since it was added; `size_chart`, `description`, and `image_urls` now rely on the same one.
   - Response on success: `200` with `{ productId, updated: { ...only the fields actually written } }` — the same partial-update contract on the way out as on the way in. Every validation failure is a specific `400` (unknown product id, wrong field type, over-length field, malformed/oversized `sizeChart`, disallowed image URL naming which one and why, no optional fields provided) — never a vague "invalid request". A genuine DB failure is a `500` with a generic message; the real error is logged server-side only, never in the response body.
   - Single-table, single-row `UPDATE` — no multi-table rollback complexity like `curate-match`'s group+members insert, since there's only ever one row being written here.
   - There is currently no "list curated fields" endpoint beyond the normal public `products` read path — like `curate-match`, this is an internal curator tool, not a queryable admin API.

8. **Give the frontend the project URL/key.** Locally: copy `.env.example` to `.env.local` in `fitcart-ai/apps/web` and fill in `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`. For the GitHub Pages deploy: add both as repo secrets (Settings → Secrets and variables → Actions) and reference them in `.github/workflows/deploy.yml`'s build step — this is a deliberate decision to make (see the PR/commit description for the open question of whether to keep the mock-API fallback for signed-out visitors once this is live).

## Known limitations

- The `fetch-product` parsers are plain-`fetch` HTML scrapers with no headless browser. Several target stores render price and size-chart data via client-side JS, which a plain fetch never sees — those parsers fall back to JSON-LD (`schema.org/Product`) when the page includes it, and return `null` otherwise. This is a structural ceiling, not a bug — a headless-browser fetch service would be a separate, heavier follow-up.
- **Confirmed against real live product pages (2026-09-01), all six target stores currently fail**, each in a different way, all consistent with the point above:
  - Meesho, AJIO, Nykaa Fashion: the fetch itself is rejected with `403` (server-side bot detection blocking the request before any HTML is returned).
  - Myntra: the fetch fails at the HTTP/2 protocol level (`stream error ... unexpected internal error`) — Akamai-style edge mitigation resetting the connection, not a code bug.
  - Amazon, Flipkart: the fetch itself succeeds (`200`), but the parser can't extract anything (`422 Could not parse this page`) — almost certainly a bot-check/placeholder page served instead of real content, not the real product page a browser sees.
  - None of this is fixable by tweaking headers/User-Agent — it's the sites' bot detection (Akamai/Cloudflare-class), the same reason PA-API/the affiliate program exist as the *intended* route for Amazon/Flipkart. Making the others work for real would need a headless-browser fetch (real Chrome, not a plain `fetch()`) and likely rotating egress IPs — a materially bigger, costlier undertaking than this scraper, and one to decide on deliberately rather than assume.
- Each parser file has a comment noting what to check in that store's `robots.txt` before pointing real traffic at it. - **Outbound-link allowlist.** `search-products` drops (logs + omits, doesn't error the whole provider) any listing whose `productUrl` isn't on that store's allowlisted domain set (`urlAllowlist.ts`: Amazon must be `*.amazon.in` or `amzn.to`; Flipkart must be `*.flipkart.com`, `fkrt.it`, or `dl.flipkart.com`; Meesho must be `*.meesho.com`; Myntra must be `*.myntra.com`; AJIO must be `*.ajio.com`; Nykaa Fashion must be `*.nykaafashion.com`) — defense against a compromised/buggy upstream response smuggling an untrusted outbound link into the catalog. This check is skipped for mock-mode listings (which intentionally point at `example.com`), but applies to scraped listings exactly like real API results (see the entry below).
- **Search-results scraping fallback — confirmed against real live search pages, twice, with two different outcomes (2026-09-02).** Unlike `fetch-product`'s single-product-page scraper (2026-09-01 entry above), this is a *search-results-page* scraper (`search-products/scraping/`), used only when a store's real API isn't configured — see 7d above for the resulting `scrape_blocked` / `scrape_failed` statuses. Both the parser logic AND the deployed function's real network behavior were tested live (not assumed), and the two runs disagreed with each other in an important, honest way:
  - **First isolated test run (single ad-hoc request per store, from a dev machine, before any repeated hits): both stores worked.**
    - **Amazon (`https://www.amazon.in/s?k=...`):** a real `200` with the full search-results page — zero JSON-LD blocks, but its `data-component-type="s-search-result"` tile markup was real and reliably parseable: **60 out of 60** result tiles yielded a usable title, price, MRP, image, and ASIN via the regex-based HTML fallback (`amazonSearchScraper.ts`).
    - **Flipkart (`https://www.flipkart.com/search?q=...`):** a real `200`. It DID include one JSON-LD block (`@type: "ItemList"`), but every `itemListElement` only carried `name`/`url`/`position` — **no price at all**, not enough to build a real listing (D-014 forbids fabricating one). The page also embeds `window.__INITIAL_STATE__` (a large Redux-style state blob), whose `PRODUCT_SUMMARY` widgets carried complete title/brand/price/MRP/image data: **40 out of 40** sampled products had all fields present and were turned into real listings (`flipkartSearchScraper.ts`).
  - **Second test run — a handful of subsequent requests from the same dev-machine IP, and separately, the actual deployed Edge Function invoked live via `curl` against `https://glbrmvyffrxhxqumecxd.supabase.co/functions/v1/search-products` — both stores got blocked:**
    - **Amazon** started returning a real `503` whose body is Amazon's own explicit anti-automation page (`"To discuss automated access to Amazon data please contact api-services-support@amazon.com"`, `"It's rush hour..."`) — this is Amazon's documented bot-detection response, not a generic outage, and it was reproduced both from the dev machine (after a few requests) and from the deployed Edge Function. The scraper correctly reports this as `scrape_blocked` with `reason: "HTTP 503 from Amazon"` — it does not retry, rotate IPs, or otherwise try to defeat the block.
    - **Flipkart**, when hit from the deployed Edge Function's network, did not return any response at all within 90+ seconds (consistent with an anti-bot tactic of accepting the connection and then never sending data, rather than an outright rejection). This is why `flipkartSearchScraper.ts` / `amazonSearchScraper.ts` now wrap every request in a 15s timeout (`scraping/htmlUtils.ts`'s `fetchWithTimeout`) — without it, a hung upstream request would hang the whole provider (and risk the platform's own function-level timeout) instead of cleanly resolving. With the timeout in place, a hang now correctly resolves to `scrape_failed` with `reason: "Request timed out after 15000ms"`.
  - **Bottom line, stated plainly:** the scraping fallback's parsing logic is real and does work against real markup — this isn't a stub. But in practice, both stores' bot detection kicks in quickly under any repeated or automated-looking traffic pattern (exactly the same class of Akamai/Cloudflare-style mitigation documented in the `fetch-product` 2026-09-01 entry above), so **`scrape_blocked`/`scrape_failed` should be expected as the common case in production, not the exception** — a first request in a while may succeed, but do not assume sustained availability. Neither scraper does anything to work around this (no UA rotation, no CAPTCHA-solving, no proxies, no retries) — that's a deliberate honesty boundary, not a gap to silently patch with fabricated data.
  - **Fractional-price rounding (fixed 2026-09-02).** `products.price`/`.mrp` are `integer not null` and `index.ts`'s `upsertListings` sends a whole store's listings in one `.upsert()` call, so a single fractional value would fail the entire batch. Both scrapers' data paths now `Math.round()` before a listing is built: Amazon's single path and Flipkart's JSON-LD path via `parseIndianPrice` (`scraping/htmlUtils.ts`), and Flipkart's `__INITIAL_STATE__` path (the one that actually carries live price data, per the JSON-LD note above) directly in `listingFromProductValue` (`flipkartSearchScraper.ts`) — matching the same convention already used by the real API adapters (`amazonPaapi.ts`, `flipkartAffiliate.ts`).
